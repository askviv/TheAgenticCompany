# SimPy and τ-bench compatibility for enterprise simulation

**Status:** upstream integration implemented; focused component tests passed; one neutral provider transport probe; no actor conversation or scenario execution performed
**Reviewed:** 2026-10-29
**Scope:** SimPy clock/event behavior and τ-bench customer domain/orchestration/evaluation reuse, including B1 delayed shipment and E1 inbound customer complaint. This records the compatibility review and implemented integration boundary; it is not evidence of a completed B1/E1 or S01 scenario.

## Decision

Both projects are useful as **libraries behind coordinator-owned adapters**, not as plug-ins or as the coordinator itself.

- Use SimPy as an in-memory discrete-event scheduler. Persist scenario inputs and committed canonical events outside SimPy, and reconstruct the SimPy environment from those records on reset/replay. The framework does not supply durable event storage, cross-service transactions, or an enterprise event bus.
- Use τ-bench's native Task/UserScenario/UserSimulator and action/communication evaluator APIs in an isolated worker; bridge customer turns to the existing Mailu SMTP/IMAP service. Built-in τ-bench tasks/domains do not implement this mail path.
- Keep the coordinator as the authority for simulated time, hidden shipment/customer truth, event idempotency, durable trajectory/event records, and cross-system invariants. Let workplace, ERP and mail services remain authoritative for their own records.
- B1 uses coordinator/SimPy time, not an agent-visible clock API. E1 uses an isolated τ-bench task/user simulator with private customer data and separate diagnostic evaluation. No B1/E1 or S01 outcome has been executed or proven here.

## What τ-bench provides for a custom customer domain

Source inspected in `src/tau2/data_model/tasks.py`, `src/tau2/environment/{environment,tool,toolkit}.py`, `src/tau2/orchestrator/orchestrator.py`, `src/tau2/user/user_simulator.py`, and `src/tau2/evaluator/*`:

1. **Task and private customer instruction model.** `Task` contains `user_scenario`, optional `initial_state`, `evaluation_criteria`, user-tool allow-list (`user_tools`), and an optional deterministic `agent_opener`. `UserScenario` separates persona from instructions; structured instructions include domain, reason, known/unknown information, and task instructions. This can represent a customer's complaint, private facts, disclosure conditions, and goal. The coordinator must keep the scenario/task source private from the tested agent.
2. **Custom environment and tools.** `Environment` takes domain name, policy, agent `ToolKitBase`, and optional separate `user_tools`. Tools are Python methods decorated with `@is_tool(ToolType...)`, with schemas/signatures exposed by the toolkit. This gives a practical pattern for a new `customer_email` domain: narrowly scoped mailbox/customer operations, explicitly separated agent and simulator tool sets, and typed policy/instructions. It does not supply an adapter to Mailu, workplace channels, ERP, or coordinator APIs.
3. **User simulation.** `UserSimulator` assembles a system prompt from shared simulation guidelines, task instructions, and persona, and is configured with an LLM. The implementation invokes upstream `get_init_state` and `generate_next_message` in an isolated worker, while the coordinator bridges completed turns to its existing Mailu gateway. Customer facts remain simulator-only task instructions, and customer messages still require Mailu receipts. A neutral transport probe did not pass an actor task/prompt or simulate a customer conversation. Customer behavior and scenario suitability remain unmeasured.
4. **Orchestration.** The orchestrator coordinates agent/user/environment turns, records a trajectory, has step/error limits and accepts a seed. The seed is a reproducibility input for the run, not a durable resume protocol or guarantee that external LLM outputs repeat. The runner/orchestrator are designed around bounded interactions, not a multi-day, event-triggered job engine with durable wakeups and approval resumption.
5. **Evaluation hooks.** `Task.evaluation_criteria` supports environment assertions, expected actions, and communication criteria. The isolated worker exposes τ-bench `ActionEvaluator` and `CommunicateEvaluator` with substring scoring; it does not use the semantic LLM judge. The coordinator preserves these results as a separate customer-domain diagnostic without changing TAC scoring. Coordinator checks remain authoritative for business state, Mailu receipts, approvals, and isolation.

### E1 mapping: complaint received by email

Implement this as a τ-bench-inspired domain/adapter, not a voice task with renamed prompt text:

- **Channel:** customer message enters the existing Mailu SMTP ingress and becomes visible through IMAP. The employee agent reads and replies using the established email pathway. The existing mail integration is documented in `deploy/single-host/company-mail.md`; its company flow explicitly verifies inbox delivery and exact SMTP/IMAP receipts. Respect the existing authenticated SMTP/IMAP setup and sender identity checks.
- **Separate information views:** coordinator/evaluator hold scenario truth and customer goals; customer simulator receives only its private `UserScenario`; the agent sees only inbox contents, workplace records and approved customer-facing tools. Do not expose τ-bench task JSON, initial-state fixtures, evaluator expected state, or coordinator event administration to the agent. A customer response is based on the customer simulator’s instructions and only facts actually provided to it/visible in the thread.
- **Bridge:** a custom domain service converts a mail delivery receipt to the τ-bench conversation/message representation and routes the agent reply through SMTP. It must persist Message-ID, mailbox UID/UIDVALIDITY, actor IDs, content hashes, version/run IDs and outcome references, consistent with the existing mail workflow; it must reconcile uncertain sends instead of blindly resending. Avoid duplicating the mailbox or storing SMTP/IMAP credentials in scenario fixtures.
- **Policy:** encode the complaint-handling policy as the agent-facing domain policy and tool-side authorization invariants. Keep private customer goals and evaluation criteria out of that policy unless the scenario intends them to be disclosed. Any consequential action must go through the existing approval/authorization boundary; τ-bench tool labels alone are descriptive, not an enterprise authorization layer.
- **Evaluation:** use deterministic assertions for correct case/customer/thread linkage, required investigation and response, policy/approval compliance, exact inbox/outbox receipt, and no prohibited state mutation. Action checks can require relevant tool calls, but end-state assertions should carry the business correctness check. Score response content separately using explicit deterministic required facts/communication criteria where possible. If using a language-model judge, mark that result as model-judged and do not claim it is deterministic.
- **Not supplied upstream:** email transport integration, mail user interface, mailbox state isolation, Mailu credential management, reliable delivery/reconciliation, enterprise approvals, workflow resumption, customer-record identity mapping, or a multi-service evaluation oracle. These are adapter/coordinator work.

## SimPy, persistence, deterministic replay, and the clock boundary

SimPy 4.1.2 `Environment` is a local in-memory event queue with numeric simulation time. Processes yield events/timeouts; `env.run(until=...)` or stepping APIs drive the queue. Equal-time events are processed in queue scheduling order. A bounded check ran under isolated CPython 3.12.12 after installing the official 4.1.2 sdist: `simpy.__version__` was `4.1.2`, and three processes registered in order with `timeout(5)` fired at time 5 in that same order. This proves the package imports and that one equal-time case behaves deterministically; it is not a durable replay test or an enterprise integration test. The scheduler itself does not persist the queue, serialize process state, provide a database transaction, or replay a durable cross-service log. SimPy is therefore appropriate for calculating and ordering events, but cannot be treated as event storage or a durable scheduler.

For the simulation coordinator:

1. Persist each scenario’s seed, initial state, selected package/source versions, and scheduled event definitions (stable event ID, event type, due simulated time, payload reference, source, and deterministic tie-break sequence) in coordinator-owned durable state.
2. Give only the privileged controller the ability to schedule/advance/pause simulation time. Agent tools must not expose `advance_time`, hidden pending-event inspection, raw coordinator state, or direct SimPy environment access. The agent learns a shipment delay through an allowed channel such as Mailu or employee chat.
3. At each controller advance, derive the next ordered events from durable records, run SimPy to the requested simulated timestamp, and commit canonical event outcomes through an idempotent outbox/receipt boundary. A unique event ID plus durable processed status prevents duplicate delivery. Reconcile downstream receipts before retrying uncertain writes.
4. For reset/replay, rebuild a fresh SimPy `Environment` from the same pinned version, seed and ordered event definitions, then replay committed canonical events into adapters’ scenario state. Do not serialize a live generator/process graph as the durable replay contract. A trajectory replay is reproducible only to the extent that the event inputs, tie-break order, adapter behavior and seed are fixed.
5. Keep simulated time separate from host wall time. Advancing from Day 2 to Day 5 is a controller operation; it should not require waiting three real days. Real-time sleeps/timers should not implement scenario time or synchronization. Bounded waits for transport receipts can be operational timeouts only and must produce explicit failure when exceeded.

### B1 mapping: delayed shipment

Schedule an expected Day 2 delivery and a seeded transport-disruption event that revises ETA to Day 5. The event should update coordinator-owned physical shipment truth once; ERPNext must not receive a goods receipt until a legitimate receipt is evidenced. Deliver the delay to the agent through the selected business channel (for example, an inbound logistics email or employee message), not through privileged event inspection. The agent’s allowed tools should support locating the related PO/shipment, following up, recording the updated ETA, and communicating to stakeholders. Evaluate against durable canonical state and receipts: one delay event processed, ETA = Day 5, no premature goods receipt, correct shipment/PO linkage, and required stakeholder update. A run passing these assertions remains an implementation/evaluation result; it is not implied by framework selection.

- **Mail and evaluator boundary:** [`actor_protocol.py`](../../servers/simulation/actor_protocol.py) and [`actor_client.py`](../../servers/simulation/actor_client.py) define versioned authenticated RPC DTOs. Responses enter the coordinator's existing outbox/Mailu path. The worker's private `/v1/evaluate` calls upstream action and substring evaluators without a judge; the coordinator returns this diagnostic separately from TAC scoring.
- **Verification:** `tests/test_customers.py` and `tests/test_tau2_customer_worker.py` passed (8 tests) in the isolated τ Python 3.12 lock environment. They mock only the Codex transport and cover native Task/UserSimulator state/message behavior, idempotent worker turn replay, action/substring evaluation positive/negative cases, and safe unexpected-evaluator errors.
