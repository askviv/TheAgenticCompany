# Whole-company virtual-time world

## Target architecture

Run a dedicated Ubuntu VM directly on the Linux host using QEMU/KVM, managed
as a host service. Run the existing company Docker Compose projects inside
the VM. Containers share the guest kernel and therefore its time domain.
Do not install a time-dilation kernel on the physical host or attempt to obtain
an independent kernel by running an ordinary Docker container.

The guest requires a modern-kernel port of system-level time dilation. The
timekeeper and timer machinery must use a coherent scaled time source: wall
time, monotonic time, boot time, kernel timer deadlines and vDSO clock reads.
Filesystem timestamps must be generated by this same guest time domain. A
guest clock-rate control changes the multiplier while preserving continuity.
Guest NTP and hypervisor time synchronisation must not override that clock.
This is custom kernel engineering, not an existing QEMU/KVM speed setting.

The guest clock replaces coordinator-only acceleration: the coordinator uses
guest time at rate one, preventing double acceleration. Company applications,
databases, mail, chat, documents and benchmark services all run in the guest.
Their normal schedules and business dates consequently use the same clock.

## Kronos compatibility

Kronos documents a modified Linux 4.4.50 kernel and Ubuntu 16.04.5 installation.
It is not a drop-in dependency for the current host. Use its virtual-time
design as a reference for the guest implementation; do not replace the host
kernel or assume its old kernel can support the current application images.
The implementation must target a guest kernel compatible with the company's
current container requirements.

## Deployment and data

Provision a separate guest system disk and persistent company data disk.
Initially copy existing data and configuration, preserving the original
deployment for rollback. A final migration requires quiescing writers and
taking a consistent final copy before switching the existing application
addresses to the guest. Never run two writable deployments against one data
directory. Retain original volumes and snapshots until migration is accepted.

Retire the application clock wrappers. Persist the clock epoch and rate with
the guest world, with an explicit policy for whether powered-off time accrues.
Keep clock-control access on the host so it remains reachable if guest services
fail. Snapshot disk and clock state together when creating a restorable world.

## External boundary

The host remains on real time. The confirmed five-real-minute unread-email
handoff deadline is tracked by a host-side controller. Viv, remote model calls
and external mail systems retain their own clocks; their delivery timestamps
cannot be changed by the company guest. Clock acceleration does not accelerate
CPU work or external inference. Connections crossing this boundary need
explicit transport and certificate handling; do not disable TLS verification.

## Implementation sequence

1. Implement the guest kernel time-dilation mechanism and host rate control.
2. Manually establish coherent guest dates, waits, timers and file timestamps
   with an empty guest, without company experiments or Viv interaction.
3. Install the existing Compose stack inside the guest with copied data.
4. Apply record-retention policies before acceleration; virtual expiry is real
   application behaviour and must not silently delete preserved records.
5. Coordinate the final data copy and address switch, retaining rollback.

The implementation lives in [`deploy/virtual-time-world`](../../deploy/virtual-time-world/README.md), including the pinned kernel patches, VM provisioner, clock supervisor and guest lifecycle units. Follow the [migration runbook](virtual-time-migration.md) to move an existing company without replacing its records. The VM runs Docker; it is not itself an ordinary Docker container.
